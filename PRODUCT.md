# Бот заявок в общий чат 8 квартала

Бот помогает администраторам общего чата 8 квартала (8 фазы) микрорайона Переделкино Ближнее рассматривать заявки на вступление. Он задаёт заявителю два вопроса в личке и собирает ответы в карточку. Решение принимает администратор. Единственное автоматическое решение — отклонение по истечении срока ответа.

## Кто и что может делать

| Участник | Возможности |
| --- | --- |
| Заявитель | Подаёт заявку через ссылку-приглашение в основной чат. Отвечает боту в личке. После отклонения может подать новую заявку. |
| Администратор основного чата | Принимает или отклоняет заявку кнопкой в карточке. В личке с ботом смотрит состояние сервиса и статистику через `/status` или `/health`. |
| Бот | Обрабатывает заявки только из `MAIN_CHAT_ID`. Публикует карточки в `ADMIN_CHAT_ID`, который может указывать на группу или личку. Для решения проверяет и место нажатия, и роль нажавшего в основном чате (`creator` или `administrator`). |

## Жизненный цикл заявки

В таблице указаны ожидаемые переходы поля `requests.step`. Сценарии, в которых код сегодня нарушает этот порядок, перечислены ниже.

| Событие | Новый шаг | Что видят участники |
| --- | --- | --- |
| Telegram прислал новую заявку из основного чата | `resident` | Бот спрашивает в личке, живёт ли человек в 8 квартале. Приветствие сразу объясняет оба варианта: нажать «Да» и написать дом или нажать «Нет» и написать квартал. Для первого сообщения бот использует `user_chat_id` из заявки. |
| Человек выбрал ответ | `place` | Бот сохраняет выбор, показывает подсказку при нажатии и обновляет приветствие. Затем ждёт текст от заявителя. Сбой редактирования не прерывает опрос. |
| Человек прислал адрес или квартал | `review` | Администраторы получают карточку, заявитель — подтверждение. Код обрезает пробелы по краям и просит сократить текст длиннее 50 символов. |
| Бот не смог доставить приветствие | `review` | Администраторы получают карточку с пометкой о проблеме с личкой и могут уточнить сведения вручную. |
| Администратор принял решение по текущей карточке, Telegram его выполнил | `approved` или `declined` | Бот обновляет карточку, убирает кнопки, записывает решение и пытается уведомить заявителя. |
| С момента создания заявки прошло больше `EXPIRE_HOURS`, и человек всё ещё на шаге `resident` или `place` | `expired` после отклонения в Telegram | Бот записывает автоматическое решение и пытается уведомить заявителя. Планировщик запускается раз в час. При штатном значении 48 часов отклонение происходит на ближайшей проверке после дедлайна. |

Для `review` срок автоотклонения не действует. Текстовое сообщение на этом шаге получает ответ о том, что решение ожидается. При новой подаче предыдущая попытка должна остаться в истории, а анкета начинается заново.

## Что учитывает администратор

Карточка объединяет самоотчёт заявителя и доступные сведения Telegram. Она показывает ответы, имя и ссылку на профиль, Telegram ID, username, наличие фото и Premium, язык, примерный период регистрации по ID, время до первого ответа и историю попыток. При наличии данных добавляются bio, личный канал, источник приглашения и членство в настроенных чатах домов.

Оценка возраста аккаунта и пометка о быстром ответе — эвристики для администратора. Код не использует их для автоматического решения. При интерпретации карточки важно учитывать, что сейчас ошибка чтения фото выглядит как отсутствие фото, а неудачная проверка членства может выглядеть как отсутствие человека в чате дома.

## Боевое развёртывание

Бот работает в Cloudflare Workers. Имя Worker — `join-request-bot`, точка входа — `src/index.ts`. Привязка `env.DB` указывает на базу Cloudflare D1 `join-bot`. [Боевой адрес](https://join-request-bot.msk-pb-8-district.workers.dev/) · [Конфигурация Wrangler](wrangler.toml)

| Операция | Как выполнить из корня репозитория |
| --- | --- |
| Опубликовать код | `npm run deploy` запускает `wrangler deploy`. |
| Применить новые миграции к боевой D1 | `npm run db:remote` выполняется отдельно от публикации кода. |
| Зарегистрировать вебхук при настройке или смене адреса | `npm run webhook -- https://join-request-bot.msk-pb-8-district.workers.dev`. Скрипт загружает `.dev.vars`. Для регистрации нужны токен боевого бота и тот же `WEBHOOK_SECRET`, что задан у Worker. |
| Посмотреть логи | `npx wrangler tail` показывает события в реальном времени. В панели Cloudflare откройте **Workers & Pages → join-request-bot → Logs**. |

Для мониторинга используйте [GET /health](https://join-request-bot.msk-pb-8-district.workers.dev/health). Обработчик возвращает HTTP 200, если проходят проверки D1 и вебхука Telegram, и HTTP 503 при сбое. Поле `pending` показывает число событий в очереди доставки Telegram.

**Проверка 18 ноября 2026 года.** Боевой адрес `/health` вернул HTTP 200 и `{"ok":true,"db":true,"webhook":true,"pending":0}`.

## Известные расхождения и критерии приёмки

Это открытые дефекты. Для каждой строки последняя колонка задаёт проверяемый результат исправления.

| Сценарий | Текущее поведение | Критерий приёмки |
| --- | --- | --- |
| После второго ответа не удалось отправить карточку администратору | Заявка может остаться в `review` без карточки. Следующее сообщение получает ответ «ждите решения». | После временного сбоя публикации карточка доставляется без повторной подачи заявки. |
| Планировщик выбрал просроченную заявку, затем Telegram вернул временную ошибку либо обработчик уже принял последний ответ | Код игнорирует ошибку отклонения и безусловно записывает `expired` по ID пользователя. | Временный сбой оставляет возможность повторить операцию. Заявка, успевшая перейти в `review` до начала отклонения, остаётся на рассмотрении. |
| Человек отозвал заявку и подал новую, администратор нажал кнопку старой карточки | В кнопке записан только ID пользователя. Обработчик может применить решение к новой попытке ещё во время опроса. | Решение действует только на текущую карточку попытки в `review`. Нажатие старой кнопки не меняет заявку и не вызывает одобрение или отклонение в Telegram. |
| Telegram повторно доставил тот же `chat_join_request` с прежним `update_id` | Бот архивирует текущую заявку, сбрасывает ответы и снова отправляет приветствие. | Повтор события сохраняет ответы и шаг, не добавляет строку в архив и не дублирует приветствие. Действительно новая заявка запускает новую попытку. |
| К моменту нажатия кнопки заявку уже обработали вручную или отозвали | При `HIDE_REQUESTER_MISSING` и `USER_ALREADY_PARTICIPANT` итог в базе и ответ администратору зависят от нажатой кнопки. | Карточка, журнал и статистика отражают подтверждённый исход. Если исход установить нельзя, интерфейс сообщает, что заявка уже недоступна. |

## Локальная проверка

Из корня проекта команда `npm run typecheck` проверяет TypeScript. Отдельного тестового скрипта в [package.json](package.json) сейчас нет. Для сквозной проверки используйте тестового бота, две тестовые группы и локальную D1 по инструкции в [README.md](README.md). Команда `npm run poll` снимает вебхук у бота, чей токен указан в локальной конфигурации.

При проверке таймера учитывайте особенность реализации. Значение `EXPIRE_HOURS="0"` сейчас заменяется на 48 выражением `Number(...) || 48`. Для воспроизводимой проверки задайте положительный срок и выставьте `created_at` тестовой заявки в локальной D1 раньше дедлайна, затем вызовите локальный планировщик.
